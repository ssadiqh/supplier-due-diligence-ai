Core Components Explained

1. DueDiligenceCase Entity

File: casework/DueDiligenceCase.java

The central data model. Represents a supplier case that flows through the due-diligence workflow.

Built with: JPA annotations + Project Lombok (@Data, @NoArgsConstructor)

Field Type Purpose
id UUID Primary key (auto-generated by database)
supplierName String Supplier name from application
status CaseStatus enum Workflow state (SUBMITTED → COMPLETED)
supplierAbn String Australian Business Number
supplierLegalName String Legal entity name (from ABN lookup)
requestedBy String User who initiated the case
createdAt LocalDateTime Immutable creation timestamp
updatedAt LocalDateTime Updated when status changes

2. CaseService

File: casework/CaseService.java

Business logic layer. Orchestrates case operations and database interactions.

Key methods:
- createCase(supplierName, requestedBy)
- getCaseById(id)
- getCaseByCaseId(caseId)
- getAllCases()
- updateCaseStatus(id, newStatus)
- updateSupplierInfo(id, abn, legalName)

3. CaseController

File: casework/CaseController.java

REST API endpoints. Exposes case operations as HTTP endpoints.

Method Endpoint Purpose
POST /api/cases Create new case
GET /api/cases List all cases
GET /api/cases/{id} Get case by UUID
PATCH /api/cases/{id}/status Update case status

4. CaseRepository

File: casework/CaseRepository.java

Data access layer. Extends Spring Data JPA JpaRepository for automatic CRUD operations.

Custom query:
- findByCaseId(String caseId)

How Data Flows

User Request → API → Service → Repository → Database

  1. POST /api/cases with JSON body
  2. CaseController validates input using Bean Validation
  3. CaseService.createCase() generates unique caseId, creates entity
  4. CaseRepository.save() persists to database
  5. Response returns created case with UUID and caseId

Testing Strategy

Unit Tests: CaseServiceTest (3 tests)

  • Tests business logic in isolation using mocked repository
  • Verifies case creation, retrieval, status updates
  • No database required—fast execution

Integration Tests: CaseControllerIntegrationTest (2 tests)

  • Tests HTTP endpoints using MockMvc
  • Uses real Spring application context with H2 in-memory database
  • Validates request/response serialization and status codes

Database Schema

File: backend/src/main/resources/db/migration/V1__Init_schema.sql

CREATE TABLE cases (
    id UUID PRIMARY KEY,
    supplier_name VARCHAR(255) NOT NULL,
    status VARCHAR(50) DEFAULT 'SUBMITTED',
    supplier_abn VARCHAR(11),
    supplier_legal_name VARCHAR(255),
    requested_by VARCHAR(255),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL,
    updated_at TIMESTAMP
);

CREATE INDEX idx_cases_status ON cases(status);

Design: Single UUID primary key (no separate business ID). Simple, clean schema with just one identifier.

How to Run Locally

1. Start PostgreSQL:
   docker compose up -d

2. Build:
   cd backend && mvn clean package

3. Run:
   mvn spring-boot:run

4. Test:
   mvn test

5. API endpoint:
   curl -X POST http://localhost:8080/api/cases \
     -H "Content-Type: application/json" \
     -d '{"supplierName":"Acme","requestedBy":"user@example.com"}'

Key Design Decisions

Decision Reasoning
Spring Boot (not bare Spring) Faster development, sensible defaults, embedded container
JPA + Spring Data (not raw SQL) Type safety, automatic queries, database independence
Flyway migrations Version control for schema, repeatability, CI/CD friendly
H2 for testing (not PostgreSQL) No Docker required, fast startup, same JPA behavior
Records for DTOs Less boilerplate, immutable by default, clear intent
Package: com.supplier.diligence Generic, context-aware, not personal
